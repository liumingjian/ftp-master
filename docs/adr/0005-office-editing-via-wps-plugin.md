# Office editing through a dedicated WPS plugin build, with server-held Edit Permits

Office documents (doc, docx, wps, xls, xlsx) are edited in desktop WPS embedded in Qaxbrowser through its NPAPI plugin, driven by our own browser extension. The extension is built for this system alone: it lives on the `ftp-master` branch of `liumingjian/wps-plugin` and ships with its own extension ID, so the RoadFlow build on `master` stays untouched. It reuses the RoadFlow build's proven parts: document format validation, mounting WPS, forced revision tracking, and the Writer and ET save calls. Office editing is part of milestone 1.

The plugin's target-machine evidence (wps-plugin#38, #39, #41 and the RoadFlow acceptance results) shapes the host side in ways that would otherwise look wrong:

- **WPS does not send the browser's session cookie when it reads a document**, and it opens a login page or error body as if it were the document. A save made from the editor *does* send the cookie, so a wrongly opened document could overwrite the real one. RoadFlow avoids this only because its document URLs are readable without sign-in. We will not do that, because it would let anyone on the intranet read any file without sign-in or Effective Permission.
- **The server holds the edit, as an Edit Permit.** Clicking an edit entry makes the extension ask the application to start an edit, using the session cookie. The application checks Modify and the 25 MiB limit and records the open-for-edit Audit Event. It then issues a short-lived Edit Permit bound to the User, the file and the File Version, and returns the URLs the plugin needs: a Document Gateway URL for WPS to read from and a save URL. The plugin hard-codes no paths. The Gateway serves the File Version's bytes only against an unused, unexpired permit and marks the permit delivered once the response has been sent in full. The application accepts a save only under a delivered permit. The editor page is assembled in the host's origin, so before it unlocks editing it confirms delivery with an ordinary same-origin request. This server-side check replaces the RoadFlow design's receipt cross-check, and no CORS is needed.
- **The base version comes from the permit.** A save under a permit whose File Version is no longer the latest is accepted, creates a new File Version, and is flagged as a Stale Save in its Audit Event. There is no locking and the last save wins: the plugin cannot show a lock and has no save-as, so rejecting a save would strand the user's edits, while earlier File Versions remain restorable.
- **Saves use the plugin's two shapes.** Writer documents arrive as multipart `filedata`, `md5sum` and `filename`, and the checksum is verified. Spreadsheets arrive in the ET shape: a single `file` part with an empty filename, or a single `file` value. Either way the application validates the content, then creates one File Version and one Audit Event atomically. The editor sees only a success result, never the response body, so success is HTTP 200 with the `{Success, Message, Data}` receipt, and every failure uses a non-2xx status with `Success:false` and leaves the file unchanged.
- **WPS may change the serialization.** It saves docx as a legacy CFB Word file and xlsx as a legacy Excel file. We accept serializations from the same family (Word for doc, docx and wps; spreadsheet for xls and xlsx), keep the file's name, and record the actual format on the File Version. Malformed or cross-family content is rejected.
- **Edit entries are explicit.** The extension intercepts only links the application marks as edit entries, on the one configured ftp-master origin. Ordinary download links are never plain anchors ending in an Office extension. The extension exposes a page-visible presence marker. The application shows an edit entry only when the marker is present, the User holds Modify, the format is supported and the file is at most 25 MiB.
- **The editor opens in a new tab.** The file browser stays where it was, and returning closes the editor tab.

## Consequences

- WPS opens spreadsheets as shared workbooks to keep change history; the stored file reflects that.
- Manual acceptance on the target machine (Kylin, Qaxbrowser, WPS) opens, edits and saves a docx, a doc and an xlsx against ftp-master. It also shows three things: a missing, expired or reused permit keeps the editor locked and no save is accepted; a save without a delivered permit is refused; a Stale Save is accepted and flagged.
- The plugin work is tracked in the `liumingjian/wps-plugin` issues for the `ftp-master` build. The edit-start, Gateway and save endpoints are defined in this system's OpenAPI contract.
