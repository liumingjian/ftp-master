# Office editing through the in-house WPS plugin, with a permit-gated Document Gateway

Word documents (doc, docx) are edited with our own browser extension (`liumingjian/wps-plugin`, the `roadflow-extension` product, its browser-hosted NPAPI editor route, wps-plugin#43), which embeds desktop WPS in Qaxbrowser. We integrate only with that route, not the legacy native-messaging agent. Spreadsheets (xls, xlsx), wps files and the ET save shape are out of scope until the plugin supports them; its V1 handles DOC/DOCX only. Office editing is part of milestone 1.

Target-machine evidence from the plugin (wps-plugin#38, #39, #41) shapes the host side in ways that would otherwise look wrong:

- **WPS does not send the browser's session cookie when it reads a document**, and it will open a login page or error body as if it were the document. A later save *does* send the cookie and would overwrite the file with that wrong content. So WPS never reads from an authenticated URL. It reads from a **Document Gateway**, and the plugin's Document Identity Gate keeps editing and saving locked until three things agree: the bytes the extension read with the session, the bytes WPS opened, and the Gateway's delivery receipt.
- **The Gateway is ours, and it is gated by a one-time Edit Permit rather than by network trust alone.** The plugin assumes a customer Gateway trusted only by network location. That would let anyone on the intranet read any file without sign-in, which breaks the rule that only signed-in Users with Effective Permission reach content. We chose permits over a plain IP allowlist even though it costs one more plugin change. The extension makes its authenticated source read with the plugin's per-handoff key attached. The application checks Modify and the 25 MiB limit, records the open-for-edit Audit Event, and creates a short-lived, single-use Edit Permit that binds that key to the User, the file and the File Version. The Gateway serves the bytes only against an unused, unexpired permit whose path matches, then writes the delivery receipt. The extension looks the receipt up from its own origin, so that lookup endpoint needs CORS for the fixed extension id.
- **The edit link is a same-origin path ending in the file extension**, `/office/files/{fileId}/v/{versionId}/{name}.docx`. Its path is the `sourcePath` the plugin carries through the whole edit, so the Gateway URL and the save `fileurl` both name the base File Version without the plugin knowing about versions. A plain click on this link is the edit entry: the plugin replaces the current tab with its editor and returns to the originating page afterwards. Ordinary downloads must therefore *not* be plain `<a>` links ending in an Office extension, or the plugin would hijack them. Bytes stream through the application, bounded by 25 MiB, because neither the source read nor WPS can follow a redirect to presigned storage URLs.
- **Saves use the plugin's fixed contract.** The request is a WPS multipart body with `filedata`, `md5sum` and `filename`, authenticated by the session cookie. The application requires Modify, verifies the checksum, and accepts only DOCX/ZIP for `.docx` and CFB/OLE for `.doc`. It then creates one File Version and one Audit Event atomically. The editor sees only a success boolean, never the response body, so success is HTTP 200 with the `{Success, Message, Data}` receipt, and every failure uses a non-2xx status with `Success:false` and leaves the file unchanged.
- **No locking; last save wins.** The plugin cannot show a lock and has no save-as, so rejecting a save would strand the user's edits. A save whose base version (taken from `fileurl`) is no longer the latest is accepted, creates a new File Version, and is flagged as a Stale Save in its Audit Event. Earlier File Versions remain restorable.
- **Edit entries are shown only when the plugin is present**, the User holds Modify, the file is doc or docx, and it is at most 25 MiB. Without the plugin, a click on such a link would only stream the file, so a wrongly shown entry exposes nothing.

## Consequences

The plugin needs four changes before integration: a per-origin save-path template instead of the hard-coded `/RoadFlow/uploadfiles/OfficeSave`; a list of trusted origins, each with its own Gateway template, so ftp-master and RoadFlow can coexist; a page-visible presence marker; and passing the per-handoff key on the authenticated source read so the application can issue the Edit Permit. Its forced revision tracking, same-tab navigation and Single-Editor Assumption are kept.

Manual acceptance on the target machine (Kylin, Qaxbrowser, WPS) replaces the old cookie check. It opens, edits and saves a docx and a doc. It shows that a missing, expired or reused Edit Permit keeps the editor locked and issues no save. It also shows that a Stale Save is accepted and flagged.
